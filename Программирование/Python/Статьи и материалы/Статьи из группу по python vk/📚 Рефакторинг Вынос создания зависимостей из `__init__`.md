# Рефакторинг: Вынос создания зависимостей из `__init__`

[[📚 Пример Класс для работы с базой данных]]
## Исходный подход

```python
class Query:
    def __init__(self, host, port):
        self._connection = Connection(host, port)
```

Здесь класс `Query` сам создаёт соединение в конструкторе, что имеет несколько недостатков.

## Проблемы такого подхода

1. **Жёсткая привязка** к конкретному способу создания соединения
2. **Сложность тестирования** - нельзя подменить соединение на mock/stub
3. **Ограниченная гибкость** - только один способ инициализации
4. **Невозможность асинхронной инициализации** (если потребуется)

## Улучшенная версия (с фабричным методом)

```python
class Query:
    def __init__(self, connection):
        self._connection = connection
    
    @classmethod
    def create(cls, host, port):
        return cls(Connection(host, port))
```

## Преимущества нового подхода

### 1. Упрощение внедрения зависимостей
Теперь можно легко подменять соединение, например, в тестах:

```python
fake_conn = FakeConnection()
query = Query(fake_conn)  # Легко подменить реализацию
```

### 2. Гибкость создания объекта
Можно добавить несколько фабричных методов для разных сценариев:

```python
@classmethod
def from_config(cls, config_file):
    config = read_config(config_file)
    return cls(Connection(config.host, config.port))

@classmethod
def default(cls):
    return cls(Connection(DEFAULT_HOST, DEFAULT_PORT))
```

### 3. Возможность асинхронного создания
Фабричные методы могут быть асинхронными:

```python
@classmethod
async def create_async(cls, host, port):
    conn = await create_async_connection(host, port)
    return cls(conn)
```

### 4. Разделение ответственности
- Класс `Query` отвечает только за работу с запросами
- Создание соединения вынесено наружу

## Когда применять этот подход?

1. Когда создание зависимостей сложное или требует дополнительной логики
2. Когда нужна возможность подмены зависимостей (особенно в тестах)
3. Когда могут потребоваться разные способы инициализации объекта
4. Когда возможна потребность в асинхронной инициализации

Этот паттерн особенно полезен в крупных проектах, где важны гибкость и тестируемость кода.
